# CarWithin for Android

**简体中文**

**目标：把安卓手机的屏幕，投到极核 AE4 MAX2+ 6.2 寸仪表上。**

[![Platform: Android 10+](https://img.shields.io/badge/Android-10%2B-blue)](#下载安装) [![Status: WIP 未完成](https://img.shields.io/badge/status-WIP%20%E6%9C%AA%E5%AE%8C%E6%88%90-red)](#当前状态) [![Release](https://img.shields.io/github/v/release/Andrew8102/Carwithin-for-android?label=release)](https://github.com/Andrew8102/Carwithin-for-android/releases/latest)

> 完成度以 [开发路线图](#开发路线图) 为准，不看本文其他章节的措辞。

> **换机器继续调试的先看这里**：[docs/HANDOVER.md](docs/HANDOVER.md) —— 现状结论、参照项目给出的答案、macOS 上从零到装包、以及车机旁的现场 runbook，都在那一个文件里。
> 如果 PXC 直连在现场卡住，还有一条备用路径：**全屏预览 + 极核 App 录屏**（见该文档第 4 节），用来快速证明画面能不能上仪表。

> **协议来源**：极核 PXC/TCP 协议来自 [CarWithin](https://github.com/xmz28/CarWithin) 的 iOS 逆向实现，已按原文逐项移植为 Java；CarLife 车机端来自 [CarNine](https://github.com/xiaolu5hao/CarNine-Ninebot)。移植 ≠ 可用，都需要真机取证。

> **设计前提（非已验证结论）**：按设计，CarLife 的 HU（车机端）就是手机上的这个 App。Car+ 里的 CarLife 组件作为 MD（手机端）应在 127.0.0.1 回环暴露 7 个 TCP 端口，本 App 连上去握手、协商画布、收 H.264，全程不经过极核。
> 这个判断来自 CarNine 在 realme 真机上的记录——它配的九号仪表只负责**输出侧**，输入端同样是自己冒充 HU。本项目把该实现搬了过来，但**尚未在本机复现**。
> 若成立，则"必须先连一台 ICCOA/CarLife+ 车机"不成立，真正的前提只是**把 Car+ 拉进 CarLife 模式**（不同 ColorOS 版本入口类名不同，故提供「枚举组件」+「尝试进 CarLife」）。
> 全部入口都试过仍不监听，就走录屏投屏。

## 真机实测到哪一步（2026-11-27，OPPO PKH110 / Android 17）

只记录**真机跑出来的结果**，没跑过的一律按未完成写。

| 环节 | 结果 | 证据 |
| --- | --- | --- |
| CarLife 七端口建立 | ✅ 7/7 连通 | 日志「七个通道全部连通」 |
| CarLife 2.0 握手（版本 → 挑战 → RSA → AES → 画布） | ✅ 全通 | 日志走到「已请求开始推流」，画布 848×480@25 |
| 手机 → 本机 H.264 收帧 | ✅ 稳定 | 采集 10~18 FPS、65~124 kbps、累计丢帧 0 |
| 本机解码 + 本地预览出画 | ✅ 出画 | 预览卡显示 Car+ 车机桌面（已解码 3000+ 帧） |
| 预览触控回传（TOUCH 9340） | ✅ 可用 | 点预览即操作车机：点导航卡能切到地图页；实测坐标 1:1 对应画布（点画布中心记到 `423,239` / 848×480） |
| 推极核（PXC/TCP） | ❌ 未验证 | 仪表未上电联调；且需 1024×480，源 848×480 得缩放重编码 |
| 录屏路线（MediaProjection → 极核） | ❌ 未验证 | 一次都没出过画 |

**关键坑：Car+ 必须先冷启动。** Car+ 若已经在后台跑过，重新连接后手机只会在虚拟显示里画自己的「OPPO 智行 / 百度 CarLife+」启动页——帧一直有，画面永远停在那。先 `am force-stop com.oplus.ocar`（脚本里 `./scripts/adb-carlife.sh fresh` 一步搞定）再走「拉起 + 直连」，才会进车机桌面。这条目前只能在 debug 包里靠 adb 做，App 自己没有权限 force-stop 别的包。

## 开始使用

> 下面写的是**代码设计上应该走的流程**，不是已经跑通的步骤。第一次实测时请把每一步的实际表现（含运行日志）记下来，这本身就是最有价值的东西。

### 通用准备

1. 在仪表或极核官方 App 上**开启投屏模式**（等待手机连接）。
2. 手机连接仪表的 Wi-Fi / Wi-Fi Direct 网络。
3. 打开本 App，在「① 拉起车机互联界面」填写包名（OPPO Car+ 默认 `com.oplus.ocar`），点「拉起界面」。可勾选自动拉起。
4. 预期：App 自动发现仪表 IP、完成 RSA 身份握手，状态变为 **STREAMING**。**这一步从未在真机上成功过**，STREAMING 之后的出画更未验证。

### 两条投屏路线（② 投屏控制任选其一）

| 路线 | 按钮 | 前置条件 | 设计意图 |
| --- | --- | --- | --- |
| **录屏投屏** | 开始投屏（录屏） | 弹出录屏授权点「允许」 | 通用、不依赖车机配对，任意 App 画面 |
| **CarLife 直连（零转码）** | CarLife 直连 / 一键：拉起 Car+ 并直连 | 无（按钮自己会先等端口、再拉起 Car+） | Car+ 原生 H.264、零转码、免录屏；画面先在「本地预览」卡确认 |

两个 CarLife 按钮现在是同一套流程：**先在后台等 7 个端口（最长 30 秒）→ 0.3 秒后拉起 Car+ →
4.5 秒 / 9 秒若仍在等就换一个疑似入口补拉**。顺序不能反，反了必然错过 Car+ 那一两秒的端口窗口。

两条路线**都还没有成功案例**。选择上建议先试录屏（变量更少），CarLife 直连属于协议探索。

点「停止投屏」结束。极核老协议不支持仪表触摸反控，操作留在手机上。

> 若长时间停在「协商中」：确认仪表投屏已开启且未被其他手机占用，然后退出仪表投屏重新开启再试。若始终进不去，说明发现/握手字段与真机不符，需要抓包校正（见 [真机测试计划](docs/TEST-PLAN.md)）。

> 拉起界面失败：先在手机系统设置里确认 Car+ / CarWith 已安装，点「检测安装」查看已识别的包名；厂商定制系统包名可能不同，可手动填写后拉起。

> **CarLife 停在「等待 Car+」**：说明 7 个端口没监听，也就是 Car+ 还没进 CarLife 模式。
> 先点①「**尝试进 CarLife**」——它会枚举 `com.oplus.ocar` 里所有可疑入口、逐个拉起并每 2.5 秒探一次端口，命中就停。
> 若全部未命中，点「枚举组件」看全量类名，把可疑的填进 Activity 输入框手动试。仍不行就说明该 ColorOS 版本把入口锁在系统互联流程里。

> **「未找到可拉起界面」**：说明 Car+ 没有 LAUNCHER 入口（它是系统组件），且默认的 `com.oplus.ocar.CarlifeActivity` 在当前版本不存在或未导出。
> 点「枚举组件」列出真实类名即可定位；`resolveActivity` 对未导出组件一律返回 null，必须靠枚举才看得到。

## 调试功能

### Car+ 本地预览（设计上不接仪表也能看）

`CastEngine` 会把每一帧旁路给本地解码器（`H264Decoder`），在「Car+ 本地预览」卡里显示，
设计上不需要极核在线。此时状态显示 `RUNNING_LOCAL_ONLY`，含义是「只采集、不推流」。

> 这是本轮新加的排查手段，**尚未在真机上看到过画面**。它的价值在于把问题分段——
> 一旦出画，就说明 Car+ → 本 App 这段通了；迟迟不出画，问题就锁在握手/解密/解码这一段。

期望的对照关系（等实测填充验证）：

| 预览卡现象 | 可能原因 |
| --- | --- |
| 一直「等待 SPS/PPS」 | CarLife 握手没走完，或画布协商失败 |
| 出画但花屏 | 丢帧或解密不完整，看日志里的「解密失败」计数 |
| 出画正常、仪表黑屏 | 手机侧链路已通，问题在极核推流段（Wi-Fi、握手、型号） |

### debug 调试版

`dev-latest` 里除了正式签名的预览包，还附带 `CarWithin-debug.apk`：

- debug 签名，`versionName` 带 `-debug` 后缀，可 `adb logcat -s CarWithin` 抓全量日志。
- 与正式版**同包名**，安装前必须先卸载正式版（签名不同无法覆盖）。
- 适合排查崩溃堆栈、`NetworkOnMainThreadException`、MediaCodec 初始化失败等只能在 logcat 里看到的问题。

### 测试图验证出画

不依赖录屏授权，用 Canvas 生成彩条 / 棋盘格 / 运动帧编码推流。设计用途是**先把"极核推流"这一段单独隔离出来验证**，出问题时不至于和录屏、CarLife 混在一起：

- 在「③ 车型与调试选项」的「测试图模式」选择彩条 / 棋盘格 / 运动帧，点「保存配置」。
- 回到「② 投屏控制」点「用测试图验证出画」。
- 若仪表显示对应图案 → 推流段通了；仍黑屏 → 问题在这一段，与手机互联无关。

> 这也是**最应该第一个测的**：它变量最少。目前同样未验证。

### 帧率与码率统计

「帧率与码率」卡片每秒刷新：采集 FPS、编码 FPS、发送 FPS、码率（kbps）、累计丢帧。数值本身是本地统计的，可用来定位瓶颈：

- 采集高、发送低 → 仪表逐帧拉取慢或 Wi-Fi 带宽不足。
- 编码低 → 手机编码器负载高，可降低分辨率 / 帧率 / 码率。
- 全部为 0 → 采集或会话未启动，查看运行日志。

### 多车型调试参数

「③ 车型与调试选项」内置极核 / 九号 / 台铃 / 小牛预设，可逐项覆盖：

| 参数 | 说明 |
| --- | --- |
| 宽度 / 高度 | 编码分辨率，须与仪表物理尺寸匹配 |
| 帧率 | 目标 FPS，实际取决于仪表拉帧速度 |
| 码率 | H.264 目标码率（kbps） |
| 发现端口 | 仪表发现端口，极核默认 10930 |
| 仪表 IP | 留空自动扫描；已知 IP 可直接填写跳过扫描 |

> **重要**：只有极核 PXC/TCP 的代码写得最全（也仍未验证）。九号 / 台铃 / 小牛的预设仅提供参数与取证框架，协议栈尚未移植，选择这些车型一定不会出画。

## 工作原理

下面是**设计中的**数据流，最后一环（仪表出画）还没实现过一次：

```
来源 A（通用）：手机屏幕 (MediaProjection 录屏) → MediaCodec 编码 H.264
来源 B（零转码）：OPPO Car+ → 本机 127.0.0.1 七个端口 → AES 解密 → H.264
                 ▲ 本 App 冒充车机(HU)连入；Car+ 需先被拉进 CarLife 模式
        ↓ VideoFrame
CastEngine ─┬→ 本地预览（H264Decoder → Bitmap，设计上仪表不在线也能看）
            └→ ZeehoOutput → ZeehoConnection（PXC/TCP 四端口）
        ↓
（目标）极核 AE4 MAX2+ 仪表出画 —— 未验证
```

本地预览是刻意解耦的：仪表不在线时 `CastEngine` 只记一条日志继续采集，
状态显示 `RUNNING_LOCAL_ONLY`，帧照常进解码器。这样调 Car+ 链路时不需要极核主机参与。
这段解耦逻辑是代码层面的，是否真能出画同样待验证。

本项目的协议来自三个已有工作，属于**移植**而非复现：

| 已有项目 | 它做到了什么 | 本项目怎么用 |
| --- | --- | --- |
| [CarWithin](https://github.com/xmz28/CarWithin) | iOS 端逆向极核 6.2 寸 PXC/TCP 输出协议 | 逐行移植 `Zeeho62Legacy.swift` 的握手、媒体协商与视频帧封装到 Java；**移植结果未经真机校正** |
| [ninebot_pro](https://github.com/xmz28/ninebot_pro) | 作者称安卓端可驱动极核 6.2 寸（1024×480 @25 FPS） | 参考其参数设定；本项目未独立验证 |
| [CarNine-Ninebot](https://github.com/xiaolu5hao/CarNine-Ninebot) | 安卓端冒充 CarLife 车机（HU），收 OPPO Car+ 的 H.264 再转九号 UDP | 移植其 `CarLifeLink` 七端口协议栈与 `H264Decoder`；据此推断不需要真 CarLife 车机（该推断在本机尚未复现） |

ICCOA CarLink 因依赖专有 `icar-sdk.dex` 无法开源移植，CarLife 作为替代路线。
若 CarLife 的 HU 端确实由本 App 扮演（跑在 127.0.0.1 回环上），则不依赖任何车机配对；
唯一的外部变量是能否把 Car+ 拉进 CarLife 模式，故提供了组件枚举与自动尝试。
详见 [ICCOA 现状](docs/ICCOA-STATUS.md)。

## 仪表与传输

> 本节内容来自协议逆向文档的整理，**代码写法与真机行为未做过一致性核对**。

极核 AE4 MAX2+ 6.2 寸不走九号 UDP 5012，而是 PXC/TCP 四端口，手机监听、仪表反向连回：

| 端口 | 方向 | 用途 |
| --- | --- | --- |
| 10930 | 手机 → 仪表 | 发现与投屏请求（0x70000010 / 0x70000011） |
| 10922 | 仪表 → 手机 | 会话控制，JSON 命令 |
| 10711 | 仪表 → 手机 | 媒体控制，尺寸、身份回显、启动 |
| 10710 | 仪表 → 手机 | 视频拉帧（0x72）与 H.264 AU |

**连接。** 手机扫描网段发现仪表后，通过 10930 发起投屏请求；仪表接受后反向连接 10922 / 10711 / 10710。仪表在控制通道报 `HUName` 与 `HUID`，手机用 RSA-2048 对 HUID 原始字节做 PKCS#1 v1.5 签名并回传 X.509 公钥。

**画面处理。** 媒体通道协商 1024×480 / H.264；视频通道由仪表发 `0x72` 逐帧拉取，手机回 Annex-B H.264 AU（首帧带 SPS/PPS）。默认目标 25 FPS、2500 kbps。

**唤醒与反控。** 不需要 BLE 唤醒，投屏在仪表或官方 App 中手动开启。极核老协议不支持仪表触摸反控（媒体通道 `0x20` 明确不执行）。

完整协议摘录见 [docs/ZEEHO-PROTOCOL.md](docs/ZEEHO-PROTOCOL.md)，架构见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

## 常见问题

**现在能用吗？** 不能完整用。**录屏 → 极核这条主线一次都没在真机上出过画**。CarLife 直连已经能在这台手机上收帧并在 App 内预览出画（OPPO PKH110 / Android 17 实测），但把画面推给极核仪表还没验证过。所以现在的状态是"协议通了、界面能看到画面、但整车闭环没跑通"，不是"能用但有小 bug"。

**装了就能投屏吗？** 不一定。协议是按 CarWithin 的 Swift 实现移植的，理论上应该能对，但移植过程没有真机校正字段与字节序，第一次跑很可能卡在发现或握手。需要实机测试并回传日志。

**扫不到仪表？** 确认仪表已手动开启投屏、手机与仪表在同一 Wi-Fi、未被其他手机占用。Android 13+ 需附近 Wi-Fi 权限，Android 12 及以下需定位权限。若权限齐了仍扫不到，多半是发现包的字段不对，需要抓包对照。

**点了开始但一直「协商中」？** 退出仪表投屏后重新开启，再点开始。若仍失败，查看 App 内运行日志，按 [docs/TEST-PLAN.md](docs/TEST-PLAN.md) 脱敏后回传。这条路目前没人走通过，失败是预期结果。

**画面卡顿或花屏？** 还没有人见到过画面，所以这个问题暂时没有答案。码率与帧率按 1024×480@25 / 2500 kbps 设定，参考 ninebot_pro 安卓端的参数。

**支持投 ICCOA / Car+ / HiCar 的内容吗？** 设计上是通过录屏投"这些内容在手机屏幕上显示的画面"，不依赖车机配对——但如上，录屏这条线本身也还没验证出画。CarLife 直连是额外的协议探索。

**CarLife 直连和录屏投屏选哪个？** 先试录屏，变量少（只涉及本机编码 + 极核推流两段）。CarLife 直连要先解决"Car+ 怎么进 CarLife 模式"，再解决七端口握手，变量多两层，适合当作协议研究。

**CarLife 链路怎么自查？** 三步：①先把 Car+ 结束掉（`./scripts/adb-carlife.sh fresh`，或手动 `adb shell am force-stop com.oplus.ocar`）——不冷启动的话只会看到「OPPO 智行」启动页；②点「一键：拉起 Car+ 并直连」，日志出现「七个通道全部连通」算抢到端口；③看**本地预览卡**：能出 Car+ 桌面就说明这段通了，剩下的只是把流推给仪表。preview 已实测可出画，推仪表还没验证。

**为什么「一键」之后预览一直停在 OPPO 智行 logo？** Car+ 在连接之前就已经初始化过了，CarLife 接手的虚拟显示里画的还是它自己的启动图。结束 Car+ 进程重新拉起即可，见上一条。

**预览能点吗？** 能。手指直接点/滑预览画面即可操作车机：触点会减掉黑边、按画布比例换算成 CarLife 画布像素，走 TOUCH 通道（9340）回传给手机。画布外的手势仍然交给页面滚动，不会互相抢占。日志里每次点击会记一行 `TX TOUCH down x,y` —— 坐标对不上就是等比绘制算错了，先看预览下方的画布尺寸提示。

**为什么「拉起界面」报找不到组件？** 0.4.2 之前 `launch()` 用 `resolveActivity` 当门禁，而 `resolveActivity` 对 `exported="false"` 的组件一律返回 null——Car+ 的 CarLife 入口恰好就是这种。现在改成直接 `startActivity` 并多级回退（指定组件 → 疑似入口 → 全部枚举 → 系统入口），失败时会把每个入口的真实异常打出来。若全部抛 `SecurityException: Permission Denial`，说明该 ColorOS 版本不允许外部拉起 Car+，那就只能走录屏。

**APK 是谁签名的？** 正式签名（RSA-2048，有效期至 2056 年），可直接安装、可覆盖升级。从 0.4.4 起 debug 包也用同一把钥匙（之前 CI 每次新建 debug keystore，所以每次装都得先卸载）；另外 **ColorOS 对未备案应用会要求输锁屏密码，用 `adb install` 装不会弹这个框**。私钥不在仓库；如需换成自己的密钥，见 [docs/RELEASE.md](docs/RELEASE.md)。签名只解决安装受限，不解决能不能用。
