# 推倒重来：从第一性原理看投屏到极核/九号车机

> 2026-11-27。用户真机反馈：「连上 WiFi 也无法推流，完全不行」。
> 这份文档作废之前「两条路并行、Plan A 代码就绪只差实测」的判断。
> **先读这份，再读 HANDOVER.md。**

---

## 1. 前面做对了什么、做错了什么

一句话：**内容源全打通了，通道全靠猜。**

做对的（真机证据确凿，不用推翻）：

| 环节 | 状态 |
| --- | --- |
| CarLife 七端口自连 127.0.0.1 | 7/7 LISTEN |
| 17 步握手拿到视频帧 | 全通，8~18 FPS |
| Car+ 车机桌面出画 | 848×480，累计 4967 帧 |
| 预览触控回传 | 命中导航卡，车机响应 |
| 组网凭据 | 二维码解出普通热点 ssid/pwd，不是 Wi-Fi Direct |

做错的（这次必须承认）：

1. **从来没抓过一次包。** 协议是从 `ninebot_pro`（九号）→ `TailingProtocol`（台铃）
   → `Zeeho62Legacy`（极核旧栈）→ 我们的 Android 实现，四手转手。
   用户第一天就说「人家是九号我是极核」，这个警告一直没处理。
2. **CarWithin 主项目的极核实现用的是另一套。** 它带 `TailingIdentity` 的 RSA 身份
   和反向控制通道，我们实现了签名，但协议细节追的是 legacy 分支。
3. **「两条路并行」是错觉。** Plan B（镜像投屏）真机出过画；Plan A（PXC 直推）
   从没在仪表旁验证过，六个断点一个都没有日志证据，却被写成「代码就绪」。

## 2. 第一性原理：投屏到车机只有三条路

### 路 1：推流 Push（手机主动发，车机收）

车机要有接收端入口。极核/九号的仪表没有开放这个入口，官方也没给。
**走不通，不要再想。**

### 路 2：拉流 Pull（车机连你，发 0x72，你回一帧 H264）

PXC 走的就是这条，官方 App 和 CarWithin 主项目都用这条。
关键认知：**这不是「推流」，是「车机来拉」。** 车机不发 0x72，我们一帧都发不出去。
连上 WiFi 只是第 1 步，后面还有五个断点。

### 路 3：数据同步（发导航指令给车机，车机自己渲染）

motorplay 导航投屏走这条。画面清晰、无二次编码，但要接 motorplay 的协议，
目前完全未知。**这是「更清晰」的唯一出路，但不是现在能做的。**

我们的目标——「用安卓手机自己的车机互联软件投屏到极核/九号」——现实只有路 2。

---

## 3. PXC 拉流链的六个断点

| # | 环节 | 状态 | 怎么验证 |
| --- | --- | --- | --- |
| 1 | 连上仪表热点，拿到 IP | ✅ 已确认 | 二维码解出 ssid/pwd |
| 2 | 10930 发现请求被接受 | ⚠️ 未验证 | 看 announce 是否回 0x70000011 且 status=true |
| 3 | RSA 身份签名被认可 | ⚠️ 未验证 | 看 0x10010 之后仪表是否继续下发媒体协商 |
| 4 | 仪表反连 10922/10711/10710 | ⚠️ 未验证 | `ss -ltnp` 看三个端口有没有 ESTABLISHED |
| 5 | 仪表在 10711 发 0x72 拉帧 | ⚠️ 未验证 | 日志「视频通道收到异常拉帧」有没有出现 |
| 6 | 848×480 H264 被接受并显示 | ⚠️ 未验证 | 仪表是否出画、花屏还是黑屏 |

**这五个问号，之前一个都没有证据。** 所以「连上 WiFi 也无法推流」根本不是
一个症状，是五个可能的故障点混在一起。继续凭感觉改代码只会更乱。

## 4. 新方法论：先取证，再写代码

### 第一步（必做，零成本）：拿一次完整握手日志

```bash
./scripts/adb-carlife.sh dbg connect 30
```

把 `CarWithin` tag 的全部日志存下来。**日志停在哪一环，就是断点在哪一环**：

- 停在「投屏请求被拒 cmd=0x...」→ 断点 2，发现协议不对
- 停在「已回应 RSA2048 身份」之后不动 → 断点 3/4，签名或端口不对
- 出现「媒体控制暂不支持」→ 断点 5，辅助通道命令集不对
- 出现「视频通道收到异常拉帧」→ 断点 5，拉帧格式不对
- 发了帧但仪表花屏/黑屏 → 断点 6，尺寸/编码参数不对

### 第二步：抓包对照（根治「猜协议」）

让**官方极核 App** 投一次屏，同时抓手机和仪表之间的 TCP 包，对照我们的实现。
10930/10922/10711/10710 都是明文 TCP，抓包能直接看到命令号和 JSON 负载。

Android 侧抓包方案（任选其一）：

```bash
# 方案 A：tcpdump（需 root 或 adb root）
adb shell "tcpdump -i any -s 0 -w /sdcard/cast.pcap port 10930 or port 10922 or port 10711 or port 10710"
adb pull /sdcard/cast.pcap

# 方案 B：手机开热点给电脑，电脑 Wireshark 抓共享网卡
# 方案 C：抓包大师/HttpCanary 等 VPN 模式 App（无需 root，但可能看不到 TCP 层细节）
```

拿到 pcap 后用 Wireshark 过滤 `tcp.port == 10930 || tcp.port == 10922 || tcp.port == 10711 || tcp.port == 10710`，
逐条对比命令号与 payload。**这是唯一能终结「猜协议」的办法。**

### 第三步：按抓到的真实报文改实现，而不是按 legacy 分支猜

拿到对照后才值得动代码。优先核对：

1. announce（0x70000010）的 payload 字段——我们用 `phoneType: Android`，
   CarWithin 主项目用 `phoneType: iOS`。极核仪表可能只认 iOS 客户端。
2. 0x10010 身份应答里的 `phoneOs` / `package` / `supportFunction` 等值。
3. 媒体协商命令序列（0x204c0 / 0x20020 / 0x20030 / 0x20050 / 0x205a0 / 0x20590）
   的顺序和 payload——这段是从抓包抄的，但抄的是哪个车型的抓包需要确认。
4. 拉帧 0x72 的格式和 H264 帧前缀。

## 5. Plan B 的定位（不要丢，但要看清）

镜像投屏是**唯一真机出过画**的方案：全屏预览 → 极核 App 录屏 → 投仪表。
它的价值是**取证**：证明「CarLife → 解码 → 屏幕 → 录屏 → 仪表」这条链是通的。

它的固有代价：二次采集编码（糊）、多一跳（卡）、上下任务栏（画面小）。
这些不是 bug，是方案本身的物理限制。

**关键经验（用户实测）**：Car+ 画布尺寸要填「车机屏幕 − 上下安全区」的可用区尺寸，
不是车机整屏尺寸，否则投上去被任务栏挤小。已写进 HANDOVER 第 4 节和 App 提示。

---

## 6. 九号怎么办（另一个完全不同的协议栈）

九号（ninebot_pro）走的是 **UDP 5012 视频 / 5013 控制 + 20 字节头**，
和极核的 PXC/TCP 是两套东西，**不能共用实现**。

- 九号的协议有开源实现 `xmz28/ninebot_pro`，成熟度高于我们猜的极核栈。
- 如果目标包含九号，应该**单独开一条线**，先把 ninebot_pro 的 Android 版跑起来，
  而不是在极核栈上修修补补指望兼容。
- 极核和九号共用的只有「CarLife 内容源」和「组网」这两层，协议层必须分开。

---

## 7. 一句话总结现在的行动项

1. **停止猜协议、停止改默认值。** 先拿一次 `dbg connect 30` 完整日志，定位六个断点中的哪一个。
2. **想办法抓一次官方 App 的投屏包**，哪怕是tcpdump。这是终结猜测的唯一途径。
3. 极核和九号分开做：极核走 PXC 拉流取证，九号走 ninebot_pro 开源栈。
4. Plan B 保留为取证手段，不要当成最终方案继续优化。
